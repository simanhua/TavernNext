# Make Scene Packages the product boundary

TavernNext presents official Scene Packages rather than independent Character, Worldbook, Preset, and script libraries. A Scene owns its workspace and may include fully trusted server code. Scene SDK v2 frontend code runs as a trusted same-origin ES Module in an independent top-level browser tab. It receives a versioned Scene SDK for Save operations, but it may also access TavernNext APIs, browser storage, the document, global objects, and the network. The SDK is an application compatibility boundary, not a security boundary. Worker Threads provide timeout and crash isolation for server modules, also not a security boundary.

During development, the official catalog contains only TavernNext-bundled Scenes and is trusted as application data. A fixed UUID is the Scene identity; display names do not participate in identity or trust. No per-Scene catalog signature is used. The locally computed archive digest remains only an immutable install-path, cache, and generation-snapshot fingerprint. Browser-ready JavaScript modules, styles, and other executable assets ship inside the built-in package. A Scene Workspace uses one named tab per setup flow or Save; duplicate Save pages cannot write concurrently. Scene networking remains subject to browser CORS and TavernNext provides no cross-origin credential proxy.

Scene SDK may expose platform-owned UI primitives for layout, responsive behavior, accessibility, and safe DOM rendering. These primitives consume Scene-owned display models and actions; they do not prescribe a shared game-state schema or become another state source. A Scene Package remains responsible for mapping its canonical Scene State into those models.

Scene State is the canonical mutable state for a Save. Worldbook natural-language rules, rather than a runtime JSON Schema validator, govern field meaning and value constraints; the platform retains only structural Patch parsing and the 4 MiB state limit. Every committed change is recorded as a parent-linked transition before updating the materialized state projection. Assistant variants own their state transition: switching a tail variant restores its snapshot, while switching a historical variant with downstream messages or actions is rejected until those descendants are truncated. Attached Extension Runtime State remains a compatibility surface and is not a second source of truth for a Scene.

Generation Recipe prompt additions are produced only by the trusted server module, included in the integrity-protected prompt snapshot, and never accepted from browser input. The `mvu-json-patch-v1` adapter uses the legacy `replace`, `delta`, `insert`, `remove`, and `move` contract, accepts the legacy Analysis wrapper, applies operations independently, and records failed operations on the Message Variant without rolling back successful siblings. Manual Scene UI changes use the same SDK Patch path directly and do not invoke a server-side business-rule Action.

Conversation, Message, and Message Variant remain shared platform entities used by Scene Saves and generation. Legacy SillyTavern chat JSONL is not a product artifact: TavernNext does not inspect, import, export, or migrate old chat files. The `chat` provider API mode and chat-completion preset kind are unrelated generation settings and remain supported.
